# Story 23.3: Angular Material 22 & Theme Reconciliation

Status: pending

## Story

As the developer,
I want Angular Material and the CDK on 22 with the Upkeep theme rendering exactly as it did before,
so that a framework-currency upgrade does not silently degrade the brand work delivered in Epic 8.5 — the one kind of regression the entire test suite is blind to.

**Depends on:** Story 23.2 (Angular core must be on 22 first).

## Acceptance Criteria

1. **Given** Angular core is on 22 and Material is still held at 21,
   **When** `ng update @angular/material@22` runs and its schematics are applied,
   **Then** `@angular/material` and `@angular/cdk` are on `^22.x`, and `npm ci` resolves cleanly with **no `--legacy-peer-deps` and no `--force`**.

2. **Given** `frontend/src/styles/_theme-colors.scss` carries the header *"This file was generated by running `ng generate @angular/material:theme-color`"*,
   **When** Material 22's theming API is applied,
   **Then** the palette is regenerated (or verified still valid) for Material 22 from the **same source colors** — primary `#4361ee` (Upkeep Blue), tertiary `#0d9488` (Upkeep Teal) — and `mat.theme()` in `src/styles.scss` compiles with **no deprecation warnings**.

3. **Given** the source colors are fixed by the UX specification,
   **When** the palette is regenerated,
   **Then** the **input colors are unchanged**. Regeneration adapts the palette to Material 22's token structure; it is **not** an invitation to redesign. Any resulting change to the *rendered* color of a surface is a regression until proven intentional.

4. **Given** **40 SCSS files reference Material's `--mat-*` / `--mdc-*` design tokens**,
   **When** Material 22 renames, restructures, or removes any of them,
   **Then** every affected reference is updated to its Material 22 equivalent.
   **A token that no longer exists must be replaced deliberately — never deleted to make the build quiet.** A silently-dropped token does not fail the build; it just renders wrong.

5. **Given** the 2 SCSS files using `::ng-deep` and the 2 targeting `.mat-mdc-*` internal classes,
   **When** Material 22 changes component DOM structure,
   **Then** those selectors are verified to still match, or are rewritten. (Coupling is low by design — but internal selectors are precisely what majors break, and they fail *silently*.)

6. **Given** the visual baseline committed in Story 23.1,
   **When** `e2e/tests/visual/theme-baseline.spec.ts` runs against Material 22,
   **Then** it passes.
   **Any** diff must be: (a) reviewed by a human, (b) explicitly approved as intentional, (c) re-baselined **in the same PR**, and (d) justified in writing in the Dev Agent Record.
   **Running `--update-snapshots` to make a red baseline green is an automatic story failure.** That is the one action that converts this entire epic's safety net into theater.

7. **Given** the full suite,
   **When** `npm run build`, `npm test`, and the E2E suite run,
   **Then** all pass, and the bundle does not grow beyond the existing overage (issue #353 — currently 585.58 kB vs a 575 kB budget).

8. **Given** the migration is complete,
   **When** the app is smoke-tested live via Playwright MCP,
   **Then** the themed surfaces are confirmed correct **by eye** — dialogs, form fields, buttons, sidebar, bottom nav, tables — with screenshots saved to `screenshots/` per project convention. Automated diffs catch what they were pointed at; a human catches what nobody thought to screenshot.

9. **Given** the epic is complete,
   **When** it closes,
   **Then** the visual baseline spec **remains in the suite** as durable regression coverage — it was built for this migration but its value is permanent (and Angular 23 lands ~Nov 2026).

## Dev Notes

### This is the story where something actually goes wrong

Stories 23.1 and 23.2 are, on the evidence, likely to be uneventful — the readiness work is small and the OnPush flip looks like a no-op given the codebase's signal discipline.

**This one is different, and it is different in a specific way: its failure mode is invisible to every test you have.**

Angular Material majors drift design tokens. When they do:
- The build still succeeds.
- All 2,984 unit tests still pass.
- The entire E2E suite still passes — every button is still clickable, every form still submits.
- And the app looks subtly, cumulatively wrong: a padding shifts, an elevation flattens, a shade of blue drifts two steps off-brand.

An unresolved CSS custom property does not throw. It resolves to nothing. **That is why AC #4 forbids deleting a token to quiet the build, and why AC #6 forbids `--update-snapshots` to quiet the baseline.** Both are the fast path to a green pipeline and a degraded product. The visual baseline from Story 23.1 exists precisely because nothing else in the stack can see this class of bug.

### The measured coupling

The good news, from the epic's grounding:

| Coupling | Count | Risk |
|---|---|---|
| Files using `::ng-deep` | **2** | Low — but these pierce component encapsulation into Material's DOM, and majors restructure DOM |
| Files targeting `.mat-mdc-*` / `.mdc-*` internal classes | **2** | Low — same caveat; internal classes are **not** a public API |
| Files referencing `--mat-*` / `--mdc-*` design tokens | **40** | **Moderate — the main event.** Tokens *are* the public theming API, but majors still rename them |

Low structural coupling means this should be a token sweep, not a rewrite. Forty files is a real but bounded surface.

### The theme's provenance matters

`src/styles.scss` applies M3 via the `mat.theme()` mixin. `src/styles/_theme-colors.scss` is **generated** (`ng generate @angular/material:theme-color`) and carries the warning *"Proceed with caution if making changes to this file."*

That means the right move on drift is usually to **regenerate it** from the same source colors — not to hand-patch it. Hand-patching a generated file is how you end up with a palette nobody can reproduce.

But regeneration is not a redesign (AC #3). Inputs stay `#4361ee` / `#0d9488`. If the *rendered* result changes, that is a regression to investigate, not a new look to accept.

### Look the tokens up; do not recall them

Material token names change across majors, and model training data lags real releases by roughly a year. **Use Ref MCP to fetch the Material 22 token reference before editing SCSS** (per `feedback_critical_tools`: look up docs *before* writing code, not after hitting errors).

Guessing a token name produces a CSS property that silently resolves to nothing — indistinguishable, at a glance, from a token you correctly preserved.

### Test Scope

| Pyramid Level | Required? | Justification |
|---|---|---|
| **Unit (frontend)** | **Must stay green — but is a weak oracle** | 2,984 tests will pass whether or not the theme is correct. They catch *nothing* in this story's primary risk area. Do not read a green unit run as evidence the theme survived. |
| **Unit / Integration (backend)** | **N/A** | Zero backend code touched. |
| **E2E (Playwright)** | **Must stay green — also a weak oracle** | E2E asserts behavior, not appearance. Every E2E test can pass on a visually broken app. |
| **Visual (Playwright snapshot)** | **YES — the primary and near-only gate** | The Story 23.1 baseline is the one automated artifact that can detect Material token drift. This story exists to be judged by it. |
| **Manual (Playwright MCP)** | **YES — required** | Catches what the baseline never photographed: hover, focus, disabled, error, and empty states. The baseline covers what we thought to capture; a human covers what we didn't. |
